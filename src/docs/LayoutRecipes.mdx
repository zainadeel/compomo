# Layout recipes

CompoMo components reuse a small set of structural recipes so related controls
grow, shrink, and respond together. Consumers select components and their
documented props; internal recipe class names are not public API.

## Controls

Control density defines the complete geometry for a size: height, inline
padding, gap, icon zone, text-container inset, and radius. Buttons, Inputs,
Selects, Menu choices, and conversation rows consume the same anatomy while
retaining their own semantics, borders, surfaces, and interaction behavior.

Use each component's `size` property. Do not copy its internal padding onto a
consumer wrapper.

Some components may document an inset option for nesting inside a control of
the same size. That option reduces only the nested control's outer geometry;
it does not define a new typography or icon scale. Do not apply inset density
to ordinary standalone controls.

## Fields

Field, Input, Select, and Slider share a 4px vertical flow between
the control and supporting or error content. `ds-field` remains the preferred
composition when a persistent external label or description is required.

## Empty regions

`ds-empty-state` owns the centered message composition. The containing region
owns available size and outer padding. Repeated application layouts should
define that region once so empty, populated, and fullscreen presentations use
the same geometry.

## Chart cards

Chart cards share one body contract: the chart fills remaining space and the
optional legend remains content-sized. Use `ds-card-chart` rather than
recreating the card shell.

## Select behavior

Single and multiple Select intentionally share popup positioning, dismissal,
search focus, typeahead, and listbox keyboard traversal. Their selection and
form contracts differ by mode: scalar Select commits one value and closes, while multiple Select
toggles an array and remains open.

See **Utility → ControlDensity**, **Utility → ChromeLayout**, and the component
stories for rendered examples.
